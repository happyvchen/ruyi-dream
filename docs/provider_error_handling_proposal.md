# ToAPIs 报错分类与重试/UX 优化方案

> 目的：把 ToAPIs（Gemini 聊天 / GPT-Image-2）调用的真实报错分门别类，明确「哪些自动重试、哪些需要别的机制」，最终减少用户看到的硬失败。
> 数据来源：本地 `generation_attempts` 表 161 条失败记录（真实分布）+ ToAPIs 后台 Usage/Error 日志 + ToAPIs 文档。统计时点 2026-07-07。

ToAPIs 后台佐证：
- **Error 日志（全时段）只有 3 条**：2× `upstream error: do request failed`（用量 0，**未计费**）、1× `用户额度不足，剩余额度 $ -2.25`。
- 今天的 502 **不在 ToAPIs 的 Error 日志里、也不在 Consume(计费) 里** → 502 是 Cloudflare 边缘层错误，请求根本没到 ToAPIs 应用层，**不计费、可安全重试**。
- 成功调用都记为 Consume（计费）；实际计费模型是 `gemini-3.5-flash` / `gpt-image-2`。

关键结论：**没有一类是删除「分镜预览」引入的，也不是我们的请求组装错误**；全部是 provider 侧的网关/网络/限流/额度/输出质量问题，加上一类我方业务校验。

## 2. 分类与处理机制

### A. 瞬时网关 / 网络错误 —— 自动退避重试（安全，基本不计费）
覆盖：HTTP 502/503/504/520–524、`upstream error: do request failed`、Remote end closed、Response ended prematurely、Max retries exceeded、SSL UNEXPECTED_EOF、write timeout、异步图片任务 503。

机制：指数退避 + 抖动，上限约 3 次。
- 聊天类（选搭/剧本/打标）：**仅在"零 token 产出"时重试**，避免重复计费——502 与连接错本就零产出，天然安全。
- 图片生成：用 `objectKey` / clientTaskId 做**幂等**，重试不重复提交、不重复扣费。

UX：后台静默重试，进度显示"服务繁忙，正在自动重试 (2/3)"，不弹红错。**这一条直接消除你踩到的 502 体验**。

### B. 限流 429 —— 退避重试 + 客户端并发闸门/排队
机制：尊重 `Retry-After` 退避重试；更根本是给打标、批量成片加**客户端并发上限 + 令牌桶排队**，从源头少触发限流。UX：显示"排队中"，自动推进。

### C. 打标/长任务轮询超时（最大宗 126 条）—— 机制改造
根因：长请求在 Cloudflare ~100s 被以 524 截断（服务端可能仍在跑）＋ 我方轮询预算偏短 ＋ 打标并发过高。
机制：
1. 打标调用改**流式**（与聊天路径一致，规避 CF 524）。
2. 提高/分级轮询预算。
3. 打标并发上限 + 排队。
4. 超时不直接判死，**自动整条重试一次**再落败。
5. 幂等：同一 garment 重复打标覆盖。

UX：打标失败应优先走失败自动排队重试；用户侧保留单件重新打标入口用于个别排障。

### D. 模型输出畸形 / 截断 —— JSON 容错修复 + 一次重问（非网络问题）
覆盖：invalid JSON、Extra data、控制字符、`finish_reason=length` 截断。
机制：容错解析（剥离控制字符、提取首个完整 JSON、宽松解析）→ 截断则提高 max/精简 prompt → 解析仍失败**自动重问一次**（模型随机，二次多半成功）→ 再失败才判 `MALFORMED_OUTPUT`。UX：用户基本无感。

### E. 鉴权 / 渠道 / WAF 配置问题 —— 不无脑重试，修配置 + 熔断告警
- **HTTP 403 error code 1010**：Cloudflare 按"浏览器指纹"封禁。服务端调用被 CF 拦截，通常是请求头/UA 可疑。先加固请求头（真实 UA、去可疑指纹），少量退避重试；连续失败→熔断 + 管理员告警。
- **HTTP 403「普通用户不支持指定渠道」**：我方请求指定了普通账号无权的渠道参数，**改代码去掉渠道指定即可**，重试无用。

UX：归类为"服务配置异常，已通知管理员"，不让普通用户反复撞墙。

### F. 余额/额度不足 —— 立即停止重试，面向管理员告警充值
覆盖：`用户额度不足，剩余额度 $ -x`（后台已出现负额度）。
机制：识别余额类错误后**立即停止该任务及一键成片自动推进**，显著提示"ToAPIs 余额不足，请充值"；加**低余额阈值预警**。UX：绝不能把"没钱了"表现成"生成失败，请重试"——那会让用户白等、还继续烧不存在的额度。

### G. 业务校验拒绝（非 provider 错误）—— 走业务反馈，不重试
覆盖：`AI Stylist 方案使用了不支持的塞腰/半塞穿法`。这是我方审美/穿法校验的正常否决，应作为**选搭质量结果**呈现（或自动重选一次），不能当基础设施失败无脑重试。

### H. 自愈机制（已有，建议扩展）
`STALE_JOB_RECOVERED`（锁过期后台恢复）已在预览用到，建议推广到选搭/剧本/成片各阶段。

## 3. 跨切面的 UX 优化（按优先级）

1. **统一错误分类器**：把 A–G 映射成稳定 `error_code`（`GATEWAY_5XX / CONN_RESET / RATE_LIMITED / POLL_TIMEOUT / MALFORMED_OUTPUT / AUTH_CHANNEL / WAF_BLOCK / INSUFFICIENT_BALANCE / BUSINESS_REJECT`）。现状很多 `error_code=None`、分类埋在 message 里——**先把分类落到 `error_code` 字段**，前端才能按类给不同文案与动作。
2. **「成功 > 慢 > 失败」推广**：该原则已在成片回传实现（设计 §16.6），扩展到 styling/tagging/script——provider 5xx/连接错不立即判死，退避续跑到预算耗尽。
3. **幂等键**：图片生成用 `objectKey`/clientTaskId 幂等；聊天类只在零产出重试——两者都保证重试不重复扣费。
4. **并发闸门 + 排队**：打标与批量成片限并发，平滑限流，从源头减少 429 与超时。
5. **低余额预警 + 余额硬停**：避免负额度继续烧。
6. **面向用户的语言**：把 `HTTP 502/524/1010` 这类技术码翻译成"图片服务暂时繁忙，正在自动重试"，技术码只保留在"技术详情"里。

## 4. 落地优先级建议

| 优先级 | 动作 | 直接收益 |
|---|---|---|
| P0 | A 类聊天/图片自动退避重试（零产出/幂等前提） | 消除 502、连接错的硬失败（你当前的痛点） |
| P0 | F 类余额识别 + 硬停 + 预警 | 避免负额度空烧、误导用户 |
| P1 | C 类打标流式化 + 并发闸门 + 自动重试 | 干掉占比最大的 126 条打标超时 |
| P1 | 统一 error_code 分类器 + 前端分类文案 | 所有环节 UX 一致、可观测 |
| P2 | D 类 JSON 容错 + 重问 | 消除偶发解析失败 |
| P2 | E 类：去掉「指定渠道」、加固 UA、1010 熔断告警 | 消除 403 系列 |

> 注：以上仅为方案，未改任何运行代码。A/C 两类涉及重试与并发，实现时须遵守项目规则——重试对聊天类必须"零产出"或幂等，避免重复计费；且不得在验证阶段真实触发外部 provider。
