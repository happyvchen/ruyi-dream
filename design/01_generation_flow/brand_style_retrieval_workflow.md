# Lily 品牌风格检索与 AI Stylist 候选漏斗

## 1. 背景

`AI 智能选搭` 的业务目标不是让 Gemini 在搭配服饰全库里做一次性搜索，而是让系统先把真实商品、品牌证据和主推款展示风险组织成少量高质量候选，再让 Gemini 像品牌造型师一样做最终审美判断。

当前白色高腰阔腿裤案例暴露了两个问题：

- 候选只以压缩 tags 进入 AI Stylist，缺少真实视觉体量、衣长、厚薄和 Lily 官方风格参照。
- 生成配饰完全由 Gemini 自由补全，容易落入“项链 + 尖头高跟鞋 + 公文包”的通用职场模板。

因此新版方案采用 `品牌样本库 + 候选漏斗 + 小候选集视觉判断`。全量搭配库不直接喂给 Gemini；Gemini 只接收少量候选 outfit、必要缩略图、主推款图片和 Lily 官方风格证据。

## 2. 核心原则

```text
检索负责找候选，排序负责控噪音，Gemini 负责审美决策。
```

生产链路必须避免两种极端：

- 不把几百上千件搭配服饰的图片、缩略图或完整 tags 一次性塞进 Gemini。
- 不把 AI Stylist 降级成后端规则选 ID 后让 Gemini 写理由。

Gemini 的最佳位置是最后一公里的造型判断：在少量候选中比较哪套真正好看、符合 Lily、让主推款更好卖，并能拒绝看似合理但视觉模板化的方案。

## 3. 四层候选漏斗

### 3.1 离线资产理解层

每件搭配服饰入库并打标时，除了 `lily-garment-tags-v1`，还应沉淀用于召回和排序的轻量资产理解结果：

- 商品视觉摘要：1-2 句短 caption，描述真实颜色、衣长、体量、材质观感和主要设计点。
- 风险摘要：遮腰、过长、厚重、深色大面积、互斥品类、强视觉故事等。
- 生成友好字段：推荐穿着方式、能否塞腰、能否敞开、是否适合做内搭/外搭。
- 视觉 embedding：后续阶段使用多模态 embedding 生成，MVP 可先不落地。
- Lily 风格相似度：和官方样本库的相似度或人工标注风格簇，MVP 可先用规则/标签占位。

这些数据进入 `effective_tags` 或独立检索表，但不是前台用户要维护的 prompt。

### 3.2 主推款理解与硬过滤层

用户点击 `AI 智能选搭` 后，系统先冻结主推款输入版本并理解主推款：

- 品类：裤装、连衣裙、上衣、外套等。
- 核心卖点：高腰、腰带、领口、门襟、裤褶、垂坠、面料肌理等。
- 不可遮挡区域：例如高腰裤的裤腰、环扣、前片褶裥和裤腿垂坠。
- 视觉气质：轻盈、挺括、柔软、通勤、春夏、秋冬、强设计等。

后端先做硬过滤和风险降权：

- 排除明显互斥品类，例如主推款是裤装时，不选择其它下装作为搭配服饰。
- 降权 `coverage_risk = may_cover_hero / likely_cover_hero` 的外套、长上衣和大体量深色单品。
- 降权与主推款季节、材质、风格冲突的候选。
- 降权会把主推款变成背景元素的强设计配角。

这一步的目标是把全量 READY 素材压缩到约 100-300 件的可召回池；MVP 库较小时也必须保留过滤和降权原因。

### 3.3 召回与兼容性排序层

系统再用标签、规则、未来 embedding 和品牌样本相似度生成 Top 候选：

- 品类互补：上装、短外套、轻量马甲、内搭、可敞开外套等。
- 色彩关系：同色系、邻近色、低冲突对比色、与主推款细节呼应的低面积色。
- 廓形关系：上短下长、上收下放、外松内紧、避免上下同时厚重。
- 主推款卖点可见：腰线、领口、门襟、裤褶、裙摆等。
- Lily 风格相似度：与官方样本中的“商务时装、轻松高级、现代简洁、女性化剪裁”匹配。
- 模板化惩罚：针织 + 西装 + 阔腿裤、外套 + 连衣裙等公式不能默认高分。

这一层输出约 12-20 件单品候选，以及 3-8 套 outfit 草案。

### 3.4 Gemini AI Stylist 决策层

Gemini 最终只接收小候选集：

- 主推款图片。
- 3-8 套 outfit 草案，每套包含候选服饰 ID、短 caption、关键 tags、风险说明。
- 每套 outfit 涉及服饰的主图或缩略图；MVP 可先传 Top 候选的第 1 张图。
- Lily 官方风格证据：与本次主推款/候选最相关的 3-5 个品牌样本摘要。
- 生成配饰边界：鞋、包、首饰只能低存在感辅助，不得遮挡主推款。

Gemini 输出 `StylingPlan`，并必须说明：

- 为什么选择这套，而不是其它候选。
- 它像哪类 Lily 官方风格证据。
- 它可能在哪里失败。
- 配饰为什么存在，是否可以不要包或不要首饰。

## 4. Lily Brand Style Index

为了避免 Gemini 用通用职场常识替代 Lily 官方风格，系统需要建立 `Lily Brand Style Index`。

样本来源：

- Lily 中国官网品牌介绍、广告大片、系列发布。
- Lily 官方天猫 / 淘宝店铺公开商品标题、商品图和分类页。
- Lily 海外官方旗舰店公开商品标题和商品图。
- 品牌官方微博、小红书、抖音等公开渠道中可验证的官方内容。
- 试点客户提供的品牌 lookbook、历史棚拍图和人工选搭参考。

样本字段：

- source_type：官网、天猫、淘宝、微博、lookbook、人工导入等。
- source_url 或内部来源说明。
- season / series / category。
- image_asset_id。
- official_title。
- visual_caption。
- brand_style_tags：商务时装、轻松高级、现代简洁、女性化剪裁、功能商务、设计感针织等。
- accessory_boundary：无包、小体量手拿包、低存在感鞋、禁用公文包等。
- embedding：后续阶段使用。
- confidence / reviewed_by / reviewed_at。

`Lily Brand Style Index` 是选搭阶段的品牌证据层，不是商品事实源。最终生成的商品事实仍来自主推款图片和被选中搭配服饰图片。

## 5. 生成配饰边界

鞋、包、首饰在 MVP 阶段不入库，因此不能让 Gemini 自由生成“完整办公室套装”。

默认规则：

- 配饰可以为空。
- 首饰默认极简、低存在感；除非主推款需要领口或耳部氛围，否则不主动生成项链。
- 鞋履优先低存在感：裸色、米色、浅口、细带、低跟、乐福、简洁通勤鞋。
- 包默认可无；需要包时应小体量、侧拿或手持，不遮挡腰线、裤褶、口袋、门襟。
- 禁止自动生成“公文包”“商务手提公文包”“大体量托特包”等会把画面拉向传统职业装的配饰。
- 配饰不得成为图位重点，不做特写，不作为商品级验收对象。

`generated_accessories` 必须附带存在理由和风险说明。若配饰只是为了“凑完整 look”，应删除。

## 6. 阶段性实施计划

### 阶段 1：无需新基础设施的候选漏斗

目标：基于现有 SQLite、对象存储、Gemini 打标和 `candidate_retrieval_snapshot`，先解决明显模板化和满分误判。

范围：

- 扩展搭配服饰打标输出，增加短 caption、体量/衣长/遮挡风险、可塞腰/可敞开等字段。
- 重写候选召回为硬过滤 + 风险降权 + 多样性保留。
- 后端生成 3-5 套 outfit 草案，再交给 Gemini 决策。
- 将传给 Gemini 的候选控制在 12-20 件。
- AI Stylist 输入包含 Top 候选主图或缩略图，而不是只给 tags。
- 修正质量门：有风险不得满分；模板化、遮挡、深色厚重必须扣分。
- 配饰从自由文本改为受控边界，默认允许无包/无首饰。

验收：

- 白色高腰阔腿裤不再默认进入深色针织 + 西装 + 公文包模板。
- 有 `coverage_risk` 的外套搭强腰线主推款时，`hero_visibility_score` 不得满分。
- 输出能解释“不选择库内搭配”为什么更好。

### 阶段 2：Lily 官方样本库与品牌证据检索

目标：让 AI Stylist 的品牌判断有证据，不再只依赖抽象品牌词。

范围：

- 建立 `brand_style_samples` 或等价表。
- 导入 Lily 官网、官方天猫/淘宝、海外官方店、官方社媒和客户 lookbook 的样本。
- 为样本生成 caption、style tags、配饰边界和人工复核状态。
- AI Stylist 输入携带与本次任务最相关的 3-5 个品牌样本摘要。
- `StylingPlan` 增加 `brand_evidence` 或在 `aesthetic_diagnosis.brand_read` 中引用品牌证据。

验收：

- 方案能说明“像哪类 Lily 官方造型”，而不是泛泛写“符合 Lily”。
- 配饰建议能对齐官方样本，不再默认公文包化。

### 阶段 3：多模态 embedding 与向量检索

目标：支持几百到上千件搭配服饰和品牌样本的稳定扩展。

范围：

- 引入多模态 embedding 模型，为搭配服饰图、品牌样本图和文本摘要生成向量。
- 早期可在数据库中保存向量并用内存计算；规模扩大后迁移到 pgvector、Qdrant、Milvus 或 Vertex AI Vector Search。
- 候选召回加入图像相似度、品牌样本相似度和主推款视觉兼容度。
- 保留规则过滤作为安全边界，embedding 只负责召回和排序，不直接决定最终选搭。

验收：

- 全库规模扩大后，AI Stylist 请求体仍保持小候选集。
- 相似度召回能找到标签不完全匹配但视觉上适合的候选。
- 历史记录可追溯每次召回使用的 embedding 版本和样本版本。

### 阶段 4：兼容性 ranker 与反馈闭环

目标：从单次模型判断升级为可持续学习的品牌生产系统。

范围：

- 记录用户重选、接受、预览通过、最终下载、人工否决原因。
- 训练或规则化维护 compatibility ranker。
- 将销售/点击/采纳数据作为候选排序特征。
- 对不同系列、季节、品类维护品牌偏好 profile。

验收：

- 常见失败案例能在召回层提前降权。
- 系统越用越贴近试点客户审美，而不是每次重新依赖 Gemini 泛化判断。

## 7. 技术组件取舍

阶段 1 和阶段 2 可以在现有技术架构内完成，不需要新增基础设施。

需要新增的数据结构：

- 更丰富的搭配服饰检索字段。
- outfit 草案快照。
- 品牌样本表或 JSON 快照。

阶段 3 开始建议引入：

- 多模态 embedding 模型。
- 向量检索组件。
- embedding 版本管理。

阶段 4 再引入：

- 反馈事件表。
- compatibility ranker 或可配置排序模型。

无论阶段如何推进，职责边界不变：

```text
全库检索和排序由系统负责，小候选集审美决策由 Gemini 负责，最终视觉生成由 Image-2 负责。
```
