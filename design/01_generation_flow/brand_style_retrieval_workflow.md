# Lily 官方样本库、穿法质量信号与 AI Stylist 全量标签直投

## 1. 背景

`AI 智能选搭` 的业务目标不是让后端替 Gemini 做审美筛选，也不是只让主推款“露出来”。0.1.0 固定采用“全量标签事实直接输入 Gemini”的工作方式：后端负责冻结主推款图片、组装未归档 READY 搭配服装的全量标签事实和生产硬边界；Gemini 在 AI Stylist Prompt 约束下像品牌造型师一样完成主推款理解、方案探索、候选比较、拒绝和最终选择。

0.1.0 生产链路必须显式防住四类风险：

- 主推款视觉理解不得长期停留在任务名启发式或 `unknown` 品类。
- AI Stylist 不得为了露出主推款而安排不符合搭配服装结构的穿法，例如把厚外套、开衫或明显门襟下摆强行塞腰。
- Aesthetic Critic 必须同时判断商品可见、穿法成立、品牌成立和整体审美，而不是只看主推款是否露出。
- ShotPlan 必须服务主推款品类和商品卖点，不能用通用全身图模板替代品类图位规则。

0.1.0 方案采用：

```text
主推款图片 + Lily 官方样本证据 + 全量标签事实 + Prompt 业务规则 -> AI Stylist / Aesthetic Critic -> StylingPlan -> 按主推品类生成 ShotPlan
```

## 2. 核心原则

```text
全量标签事实负责提供库内商品事实，Prompt 负责业务判断口径，Gemini 负责审美决策，质量信号负责记录风险和驱动改进，客户审核负责最终质量判定。
```

业务策略的维护分两层：

- 自然语言判断口径、输出格式、角色职责和审美批判要求维护在 `Prompt 维护` 的 Prompt 模板中。
- 品类互斥/降权、空库内搭配优先级、配饰默认边界、质量信号阈值、外套遮挡判定等业务口径直接维护在 `Prompt 维护 -> AI 选搭` Prompt 正文中；当次渲染后的 AI 选搭 Prompt 以快照形式进入选搭 request snapshot。

后端只保留生产硬边界：合法 ID、READY/归档/删除状态、当前主推款排除、历史快照、媒体可读性、provider 调用状态和 schema 校验。连衣裙是否优先单穿、外套降权多少、哪些质量信号需要复核这类灵活业务信息不得写死在不可维护代码里。

生产链路必须避免三种误区：

- 不把几百上千件搭配服装的图片或缩略图一次性塞进 Gemini；0.1.0 只直投标签事实。
- 不把 AI Stylist 降级成后端规则选 ID 后让 Gemini 写理由。
- 不把“商品可见”当成“造型成立”。商品露出但穿法别扭、比例僵硬、色块沉闷、品牌感不足，仍然是失败。

Gemini 的最佳位置是造型判断本身：在全量标签事实中比较哪套真正好看、符合 Lily、让主推款更好卖，并能拒绝看似合理但视觉模板化、依赖姿势规避遮挡或穿法不成立的方案。

## 3. 官方样本基准

Lily 参考样本必须来自可验证渠道：

- Lily 中国官网与海外官方店公开商品图。
- Lily 官方天猫 / 淘宝店铺公开商品图、分类页和商品标题。
- Lily 官方微博、小红书、抖音等公开内容。
- 客户提供并确认可作为品牌基准的 lookbook、历史棚拍图和人工选搭参考。

当前调研确认的业务规律：

- Lily 棚拍以浅灰白背景、轻微落地阴影、商品优先和克制通勤气质为主。
- 模特姿态不是完全静止站军姿，而是轻斜正、插袋、错腿、轻走动、自然垂手、侧身转体等低幅度变化。
- 全身图用于建立完整比例，但一组图不能大面积重复全身图；裤装、半裙等下装必须有腰脚、腰膝、侧身动态或局部图来解释商品。
- 鞋包存在感低，包通常侧拿或手持，不应挡住主推款腰头、胯部、门襟、口袋、裤褶、裙摆。
- “上衣塞进裤腰”是有条件的穿法，不是裤装主推款的默认答案。柔软薄衬衫、T 恤、薄针织可全塞或半塞；开衫、外套、厚针织、明显门襟/纽扣/镂空下摆结构默认禁止全塞。

## 4. 全量标签直投工作流

### 4.1 主推款视觉理解层

用户点击 `AI 智能选搭` 后，系统必须先冻结主推款输入版本并做视觉理解，任务名只能作为辅助证据，不能作为品类主来源。

输出 `HeroUnderstanding`：

- 品类：裤装、半裙、上衣、外套、连衣裙、套装等。
- 核心卖点：高腰、腰带、金属扣、门襟、裤褶、垂坠、领口、袖型、裙摆、开衩、面料肌理等。
- 不可遮挡区域：例如裤装的腰头、门襟、口袋、裤褶、侧缝和裤脚。
- 视觉气质：轻盈、挺括、柔软、通勤、春夏、秋冬、强设计等。
- 图位需求：该品类必须覆盖哪些景别、取景范围和角度。

主推款理解结果必须进入 `StylingPlan` 和 `ShotPlan`，不能只存在于 Gemini 临场文字里。

硬验收：

- 正常生产任务不得以 `category = unknown` 进入正常选搭通过状态；若视觉理解低置信度，应进入复核或安全 fallback，而不是继续按未知品类生成通用方案。
- request snapshot 中的主推款理解来源不得长期停留在任务名启发式；任务名、SKU 和文件名只可作为辅助证据。
- `HeroUnderstanding` 中的品类、卖点、不可遮挡区域和图位需求必须在 `StylingPlan` 候选比较、拒绝理由和 ShotPlan 中可追溯。

### 4.2 搭配服装资产理解层

每件搭配服装入库并打标时，除 `lily-garment-tags-v1` 外，还应沉淀可检索字段：

- 商品视觉摘要：颜色、衣长、体量、材质观感、主要设计点。
- 风险摘要：遮腰、过长、厚重、深色大面积、强视觉故事、与常见品类互斥。
- 穿法能力：`buttoned`、`open`、`tucked`、`half_tucked`、`untucked`、`layered`、`belted` 等。
- 穿法禁忌：例如开衫/外套/厚针织不得全塞，长上衣不得遮主推裤腰，强图案上衣不得搭强设计下装。
- 生成友好字段：能否做内搭、外搭、单穿、短上装、轻层次、是否适合露出腰线。
- Lily 风格相似度：阶段 1 可用人工/规则标签占位，阶段 2 使用官方样本检索，阶段 3 使用 embedding。

这些字段进入 `effective_tags` 或独立检索表，不展示给普通用户，也不能要求用户写 prompt 来弥补。

### 4.3 全量标签事实组装层

后端只做生产硬边界，不做审美筛选：

- 只读取未归档、未删除、`READY` 的搭配服装。
- 排除当前主推款同 `code`、同输入素材或同商品身份的搭配服装，避免把主推款自己再次作为配角候选。
- 为每件搭配服装组装标签事实卡：`code`、完整 `ai_tags_json`、必要人工业务标记、复核信息和可选风险摘要。
- 不传搭配服装图片、缩略图、后端排序、兼容性分数或 outfit 草案。
- 后端只保存全量标签事实快照、prompt 快照、provider request/response 和 code 到内部 ID 的持久化映射。

标签事实卡中的 `ai_tags` 必须保持完整对象。后端不能只摘取颜色、品类、材质等少数字段来替代完整标签事实，也不能因为某件服饰“看起来可能合适”而调整顺序或写入隐性优先级。

### 4.4 Prompt 决策约束层

AI 选搭 Prompt 必须把以下判断交给 Gemini，但要明确判定口径：

- 每次都必须比较空库内搭配、低存在感生成配饰和库内配角方案；空库内搭配是合法优秀结果，不是失败兜底。
- 连衣裙、吊带裙、套装、强设计上衣等完整单品，应先证明单穿是否已经最能展示主推款，再考虑库内配角。
- 外套、西装、针织衫、马甲等外层单品如果需要“全程敞开、披挂、搭肩、手拉开、特定姿势”才能避免遮挡主推款卖点，不得仅凭这种姿势补救胜过空库内搭配。
- 若选择库内配角，必须说明它比空库内搭配更好地服务主推款，且不是仅把主推款职业化、模板化或场景化。
- 生成配饰只能低存在感辅助，不得把画面拉向传统职业装或遮挡主推款腰线、领口、裙摆、门襟和材质细节。
- `outfit_candidates` 必须包含空库内搭配候选，或在 `rejected_candidates` / `reason_summary` 中明确说明为什么空库内搭配不成立。

### 4.5 AI Stylist 决策层

Gemini 接收：

- 主推款图片和结构化主推款理解要求。
- 当前未归档 READY 搭配服装库全量标签事实卡。
- Lily 官方风格证据或品牌边界文本。
- Prompt 业务规则、Aesthetic Critic 维度和生成配饰边界。

Gemini 输出 `StylingPlan`，并必须说明：

- 为什么选择这套，而不是其它候选。
- 为什么它比空库内搭配更能服务主推款；若不成立，应选择空库内搭配。
- 它像哪类 Lily 官方风格证据。
- 穿着方式为什么真实、好看、符合该单品结构。
- 它可能在哪里失败。
- 配饰为什么存在，是否可以不要包或不要首饰。

## 5. 穿法合法性与 Aesthetic Critic

`wearing_notes` 不是自由文案。系统必须识别穿法是否被服饰结构支持，但这类业务质量问题应记录为 `quality_signals`，不直接作为普通用户可见报错。

### 5.1 穿法合法性

当 AI Stylist 输出 `tucked`、`half_tucked`、`open`、`buttoned` 等穿法时，后端必须校验：

- 输出穿法是否存在于搭配服装 `recommended_wearing_methods` 或 `wearing_affordance`。
- 若模型要新增穿法，必须说明基于图片结构为什么成立，并进入风险提示。
- 开衫、外套、厚针织、硬挺夹克、有明显门襟/纽扣/镂空下摆的上衣默认禁止全塞。
- 高腰裤可以要求“腰头可见”，但不能默认推导为“上衣全塞”。
- 半塞必须说明哪一侧/前片如何不遮挡门襟、裤褶、腰带扣。

### 5.2 审美质量信号

Aesthetic Critic 除原有维度外，必须新增：

- `wearing_method_validity`：穿法是否被单品结构支持。
- `tuck_quality`：塞腰/半塞是否平整、自然、不会制造腰腹臃肿。
- `official_style_evidence`：是否能对应 Lily 官方样本，而不是泛泛写“符合 Lily”。
- `shotplan_readiness`：该造型是否能支持按主推品类生成多角度组图。

以下情况不得满分：

- 穿法不在搭配服装允许范围内。
- 只为露出腰头而牺牲穿着自然度。
- 主推款可见但搭配服装成为局部近景主角。
- 没有官方样本证据支撑，却声称“高度符合 Lily”。
- 第 6 格备用姿态明显优于前 5 格，说明 ShotPlan 不成立。

## 6. Lily Brand Style Index

系统需要建立 `Lily Brand Style Index`，避免 Gemini 用通用职场常识替代 Lily 官方风格。

样本字段：

- `source_type`：官网、天猫、淘宝、海外官方店、微博、lookbook、人工导入等。
- `source_url` 或内部来源说明。
- `season` / `series` / `category`。
- `image_asset_id`。
- `official_title`。
- `visual_caption`。
- `shot_type`：首图、品类核心、细节、侧身/动态、标准正面、备用。
- `crop_range`：全身、近全身、腰脚、腰膝、胸腰近景等。
- `pose_tags`：插袋、错腿、轻走动、侧身、自然垂手等。
- `wearing_method_tags`：塞腰、半塞、自然下摆、敞开、扣合、层叠等。
- `brand_style_tags`：商务时装、轻松高级、现代简洁、女性化剪裁、功能商务、设计感针织等。
- `accessory_boundary`：无包、小体量手拿包、低存在感鞋、禁用公文包等。
- `embedding`、`embedding_model`、`embedding_version`。
- `confidence`、`reviewed_by`、`reviewed_at`。

`Lily Brand Style Index` 是选搭和 ShotPlan 的品牌证据层，不是商品事实源。最终生成的商品事实仍来自主推款图片和被选中搭配服装图片。

## 7. 生成配饰边界

鞋、包、首饰在 0.1.0 阶段不入库，因此不能让 Gemini 自由生成“完整办公室套装”。

默认规则：

- 配饰可以为空。
- 首饰默认极简、低存在感；除非主推款需要领口或耳部氛围，否则不主动生成项链。
- 鞋履优先低存在感：裸色、米色、黑色、浅口、细带、低跟、乐福、简洁通勤鞋。
- 包默认可无；需要包时应小体量、侧拿或手持，不遮挡腰线、裤褶、口袋、门襟、裙摆。
- 禁止自动生成公文包、商务手提公文包、大体量托特包等会把画面拉向传统职业装的配饰。
- 配饰不得成为图位重点，不做特写，不作为商品级验收对象。

`generated_accessories` 必须附带存在理由和风险说明。若配饰只是为了“凑完整 look”，应删除。

## 8. 0.1.0 技术边界

0.1.0 在现有 FastAPI、SQLite、S3 兼容对象存储、Prompt 维护和外部 provider 架构内运行。系统固定采用全量标签事实直投 AI Stylist 的方式：后端负责 READY 范围、快照、code 到内部 ID 映射、schema 校验和状态机；Gemini 负责候选理解、空库内搭配比较、审美判断、拒绝理由和最终选择；Image-2 负责分镜预览和最终单图生成。

品牌样本证据、向量检索、反馈学习和更细的上下文压缩不属于当前运行路径。若这些能力进入产品，应先更新 `tasks.md`、领域模型和数据库 schema，再实现代码。

职责边界不变：

```text
商品事实由图片负责；搭配库标签事实由系统负责组装和快照；审美与选搭决策由 Gemini 负责；最终视觉生成由 Image-2 负责。
```
