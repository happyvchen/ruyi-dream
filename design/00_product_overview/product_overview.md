# 产品总览

## 一句话定义

ruyi-dream 是一个面向电商视觉生产团队的标准化 MVP 工具。用户上传或选择一个服装货号图包，系统为该货号保存默认组图方案，再基于默认方案自动生成一组可用于淘宝、天猫主图场景的模特服装展示图。后续产品可结合 Seedance 2.0 扩展电商主视频生成。

这里的“自动生成”不是把所有信息直接交给 Image 2。产品内部应先完成素材预处理和组图策划，再由 Image 2 逐张生成。

## 当前不做什么

当前项目不做标准 SaaS，不考虑多客户、多品牌空间、团队权限、计费、模板市场、API 开放平台等能力。

当前项目也暂不做：

- 自动质量检测
- 大规模风格模板
- 自然风景、街拍、办公室等复杂场景
- 视频生成
- 全链路商品详情页设计
- ZIP 上传
- 素材图片角色识别

## 目标用户

当前目标用户是 目标品牌 内部或服务 目标品牌的运营、视觉、商品、AI 生图执行人员。

他们的核心诉求不是自由创作，而是：

- 快速把一个服装货号变成一套模特图
- 尽量接近目标品牌 既有棚拍成片质感
- 尽量减少人工 prompt 编写和反复试错
- 支持单张不满意时重生
- 能找回、复盘和恢复之前的生成任务
- 输出后可直接进入电商上传或后期精修流程

他们也不应该被要求理解 AI 生成内部机制。前台 UI 应该围绕 `拍摄任务` 展开，而不是围绕 prompt、任务包、模型输入职责展开。

## 核心入口

主生产入口：

`生成组图`

必要辅助入口：

- `服装素材`：上传与管理货号图包、查看识别结果、生成/更新默认组图方案
- `数字模特`：维护数字模特列表、头部素材和身体参数；当前阶段先维护 1 个默认数字模特
- `生成记录`：查看历史生成任务、入参快照、输出与重生过程，并可恢复到生成组图页
- `品牌调性模板`：维护 品牌历史真实图沉淀出的风格、Pose、鞋包、背景、构图边界；普通用户日常可弱化或隐藏

## 核心工作流

1. 用户进入 `服装素材`
2. 上传散图或文件夹，形成本地预览图包
3. 用户编辑货号/标题、删除图片，保存上传
4. 系统生成或更新该货号默认组图方案
5. 用户进入 `生成组图`
6. 选择货号，系统读取默认组图方案
7. 用户点击“预览”，Image 2 生成一张 2x3 分镜预览图
8. 用户满意后点击“生成”，Image 2 在同一任务下逐张生成 5 张最终大图
9. 用户对预览图或单张结果图重生、确认最终图
10. 导出最终主图
11. 用户进入 `生成记录` 复盘，或从历史任务恢复到 `生成组图`

前台默认路径应尽量短：

```text
上传/选择服装 -> 保存默认组图方案 -> 预览分镜 -> 生成最终图 -> 确认/导出 -> 记录复盘/恢复
```

## 存储与部署边界

- 媒体文件统一使用 S3 兼容对象存储，不再维护并行存储业务分支。
- 私有化部署默认使用 RustFS Docker；云端 SaaS 部署时，同一套配置可切换到 OSS、COS、AWS S3、GCS 兼容接口等。
- 图片默认是私有对象，前端通过后端签发的短期预签名 URL 直接读取。
- 当前私有图片和本地化部署场景不默认引入 CDN；只有在 SaaS 化、跨地域访问或公共分发场景明确出现后，再评估 CDN。
- SQLite 只保存业务元数据、对象 key 和调用快照；图片、生成结果和导出 ZIP 写入对象存储。

## 技术分工

| 模块 | 职责 |
| --- | --- |
| 预处理层 | 识别服装事实、维护数字模特档案、初始化 目标品牌模板 |
| 策划层 | 选择品类规则、Pose、鞋包边界、镜头取景，生成单张任务包 |
| Image 2 生成层 | 先生成 2x3 分镜预览，再基于九宫格、模特图和服装图逐张生成最终大图 |
| 人工确认层 | 单张确认、重生、导出 |
| 记录追溯层 | 保存任务级历史、图位 attempts、输入输出快照和恢复入口 |

## 产品判断

这个工具不应该把用户训练成 prompt 工程师。

前台产品语言应该是摄影和电商语言：

- 全身
- 半身
- 背面
- 侧身
- 局部
- 领口
- 袖口
- 腰头
- 裤脚
- 裙摆
- 白底棚拍
- 浅灰棚拍

底层可以使用 prompt 和多图参考，但用户主要面对的是结构化选择与确认。

prompt 不是核心产品入口。核心产品入口是 `商品事实卡`、`数字模特档案`、`品牌调性模板`、`组图方案` 和 `单张生成任务包`。

但这些核心能力不等于都要暴露给普通用户。普通用户看到的是：

- 服装摘要
- 默认组图方案
- 品牌风格摘要
- 结果和重生操作
- 任务级生成记录

系统内部处理：

- 商品事实卡
- 品牌模板命中
- Pose 模板匹配
- 单张生成任务包
- Image 2 prompt
- provider request / response
- event logs

## 生成记录原则

生成记录的主粒度是“生成任务”，不是系统事件。

- 每次整组生成一条任务记录。
- 同一个素材包重复生成一次，产生另一条任务记录。
- 单张重生记录在原任务对应图位的 attempts 中，不作为新的前台任务记录。
- 记录中应保存足够完整的入参快照、输出图、provider 请求/响应和重生过程，方便未来恢复并重新生成。
- 事件日志保留为排查和审计信息，但不作为普通用户默认看到的历史主视图。

## URL 原则

前端 URL 应能定位可恢复的业务对象：

- `/generate?sku={sku}`：生成组图页选中指定货号。
- `/generate?run={runId}`：生成组图页恢复指定历史任务。
- `/garment-skus/{sku}`：服装素材页打开指定货号。
- `/model-profiles/{modelId}`：数字模特页打开指定模特。
- `/generation-runs/{runId}`：生成记录页打开指定任务详情。

SKU 和模特使用业务 ID，生成任务使用系统记录号。临时草稿、折叠、弹窗不进入 URL。

## 成功标准

MVP 阶段的成功不以功能完整度衡量，而以能否稳定完成以下任务衡量：

> 选择一个服装货号图包和一个数字模特，生成 5 张左右风格统一、商品清晰、构图接近目标品牌 历史成片的电商主图。

如果客户认为其中部分图片可进入实际使用或轻后期使用，则 MVP 成立。
