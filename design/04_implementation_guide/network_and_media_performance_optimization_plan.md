# 百兆带宽场景下的网络与媒体性能优化方案

> 状态：下一阶段开发设计基线（低成本高收益版）
>
> 适用版本：Ruyi-Dream 0.1.0 单客户、单工作空间生产部署
>
> 目标：不引入 CDN、外部 OSS、消息队列集群或复杂企业级基础设施，优先消除无效流量和突发带宽；在真实排队点可控时，使图片浏览、AI 任务观察、大文件上传/下载与 SSH/Tabby 稳定共存。

## 1. 结论与范围

当前问题不能只根据 FortiClient 累计流量判断。VPN 计数可能同时包含项目流量、其他应用、重传和全隧道流量；“Web 与 SSH 同时卡顿”也可能来自 bufferbloat、丢包、CPU、磁盘或 RustFS 竞争。

但当前代码已经存在几项明确且高收益的问题：

1. 运行中的 AI 任务约每 1.5 秒拉取完整详情；最近任务和批次还分别约每 4 秒刷新。
2. 任务列表摘要通过完整任务装配获得，JSON 和数据库工作量偏大。
3. API JSON 尚未统一压缩。
4. 图片检查器默认加载原图，thumb/preview 缺失时还可能静默回退原图。
5. 浏览器直传固定并发为 4，容易在较慢上行或 VPN 中形成排队和 bufferbloat。
6. 页面切换时旧 GET 可能继续传输，慢响应也可能覆盖新页面状态。
7. 非首屏图片虽有部分 lazy loading，但尚未形成统一的首屏和预取预算。

本方案因此分为三类：

- **P0：应用内确定性收益项**。实现简单、风险可控，不等待完整监控平台即可执行。
- **P1：证据触发项**。只有 P0 上线后的生产数据证明仍存在对应瓶颈时才实施，不把它们预先建设成通用平台。
- **条件基础设施项**：QoS/AQM 只在确认真实排队点且具备网关或主机控制权时实施，不把不在项目控制范围内的网络能力当作应用 P0 的必然交付。

“按证据全部实施”指完成全部 P0、被生产数据触发的 P1，以及在具备网络控制条件时实施 QoS/AQM；未达门槛或不具备控制权的项目保持不做。

### 2.2 场景表统一假设

后文容量表不是生产承诺，统一采用便于比较的保守模型：

- 普通业务原图：25 MB/张；
- preview：150 KB/张；
- thumb：6 KB/张；
- 一组五张可下载成片：40 MB；
- AI 任务观察时间：5 分钟；
- 链路标称为 100 Mbps，但实际吞吐、VPN 开销、RTT 和上下行瓶颈必须现场测量；
- “时间”不写死为理论带宽换算值，生产结果必须同时记录有效吞吐、RTT、丢包和主机负载。

生产上线前使用现有 `docs/loadtest.md`、浏览器 Network/HAR、`iperf3`、`ping`、`docker stats` 和 `iostat` 采集一次同口径基线。P0 不依赖新建 Prometheus、ELK 或专用可观测平台。

## 3. 设计原则

1. **先消除错误流量，再建设调度能力**：原图误加载、重 JSON 轮询和过高上传并发优先级最高。
2. **状态轻、内容重**：运行中轮询轻量 status；详情只在详情修订号变化或进入终态时刷新。
3. **thumb 用于列表，preview 用于查看，original 只用于下载和显式精细验图**。
4. **控制峰值，不虚构减少原始字节**：上传和下载总量不能凭软件消失，优化目标是减少错误下载、失败重传和链路排队。
5. **使用浏览器与 HTTP 原生能力**：继续使用浏览器 HTTP cache，不增加 Service Worker、IndexedDB 图片缓存或自研资源缓存平台。
6. **流量治理必须可借用**：bulk 无竞争时可以使用空闲带宽；有竞争时向 API、SSH 和控制请求让路，不永久浪费 30%–40% 带宽。
7. **默认单机、单客户思维**：不为未来多租户预建用户配额、工作空间公平队列或分布式协调。
8. **不触发外部 AI 调试**：性能测试使用 mock provider、固定数据和模拟状态推进。
9. **测试数据隔离**：使用临时数据库、专用对象前缀和显式清理。

## 4. P0：七个确定性高收益优化

### P0-1 轻量基线与最小可观测

只采集能够支持本轮决策的数据：

- Nginx/FastAPI：路由模板、状态码、耗时、响应字节；
- 媒体：thumb/preview/original 请求次数和传输字节；
- 上传/下载：文件大小、浏览器并发、失败次数、有效吞吐；
- 主机：CPU、RSS、磁盘利用率、网卡上下行；
- 用户链路：RTT、丢包、TCP 重传、上下行有效带宽；
- 日志不得记录签名 URL、Cookie、Authorization、Prompt 或 provider 正文。

先使用现有访问日志、HAR 和 Runbook；只有无法回答瓶颈归属时，才新增细粒度埋点。P0 不要求先建设仪表盘，也不要求等待一个完整业务日后才能修复明显问题。

验收：可以按同一 5 分钟窗口回答 API JSON、媒体、上传和下载各自用了多少字节，以及卡顿发生时 CPU、磁盘、RTT 或重传是否异常。

### P0-2 preview-first，禁止原图静默兜底

- 所有列表、卡片、导航和胶片条只使用 thumb。
- 图片检查器首次打开使用 preview。
- “1:1 原图”必须同时表示一次明确的资源切换：用户点击后才把当前图片从 preview 切换到 original；不能只改变 CSS 缩放。
- 下载始终走 original/download，并保持 `private, no-store`。
- thumb/preview 缺失时显示占位和“预览暂不可用”，不得尝试 original；只有已创建真实修复作业时才显示“正在修复”。
- 媒体 DTO 返回 `thumbStatus`、`previewStatus` 或等价状态，至少区分 `AVAILABLE` 与 `MISSING`；前端不通过 URL fallback 猜测可用性。
- 上线前通过可重入、有界批次先补齐当前任务和常用素材的派生图，再渐进修复归档长尾；不为此引入常驻队列系统。
- 继续使用已有稳定 `/api/media` 路由、不可变 object key 和浏览器私有缓存；联调时同时检查 302 与 RustFS 最终响应的缓存头。

验收：普通列表和默认检查器 original 请求数为 0；30 图冷列表媒体小于 2 MB；10 张 preview 约 1.5 MB；派生图缺失不会触发原图下载。

### P0-3 gzip 与真正的轻量列表 DTO

- FastAPI 或 Nginx 只在一层启用 gzip；对达到阈值的 JSON/Text 压缩，不重复压缩图片和归档。
- 建议起始参数：最小 1 KB、压缩级别 5，按 CPU 实测调整。
- 任务列表建立独立 SQL/DTO，只返回任务 ID、名称、状态、进度、`detailRevision`、创建/更新时间、批次 ID、封面 thumb 和必要操作状态。
- 列表不得携带完整 StylingPlan、所有结果图、input version、attempt、prompt 或历史快照。
- 批次列表通过固定次数查询完成，不逐项调用完整 `get_generation_task_by_id()`。

验收：30 条任务列表压缩后小于 100 KB；列表查询次数不随 item 数线性增长；前端打开任务时再按需获取完整详情。

### P0-4 轻量 status、单一详情修订号与轮询协调

新增：

```http
GET /api/generation-tasks/{task_id}/status
```

建议响应：

```json
{
  "taskId": 123,
  "status": "FINAL_RUNNING",
  "stage": "FINAL_IMAGE",
  "progress": { "completed": 2, "total": 5 },
  "activeOperation": { "type": "final_image", "status": "RUNNING" },
  "detailRevision": 18,
  "updatedAt": "2026-09-21T12:00:00Z",
  "retryAt": null,
  "error": null
}
```

- 只保留一个 `detailRevision`，表示“完整详情表示是否已变化”，不用 `updatedAt` 代替。
- 任务图片、输入版本、StylingPlan、分镜或成片结果、当前资产、用户补充要求，以及未被 status 完整承载的用户可见错误等详情变化，必须通过统一后端函数在同一事务中递增 `detailRevision`。
- 只改变 status 已直接返回的进度、重试时间、运行心跳或锁租约时，不递增 `detailRevision`，避免把 status 轮询重新放大成详情轮询。
- 不允许业务代码直接更新上述详情表示而跳过修订号函数；新增写路径必须有修订号契约测试。
- status 本身直接包含用户当前需要看到的状态、阶段和五图进度，不装配媒体、StylingPlan、attempt 或历史快照。
- 当前页面首次进入取一次详情；运行中只轮询 status；`detailRevision` 变化时合并成一次详情刷新；终态无条件再刷新一次。
- 同一标签页、同一 task 只允许一个在途 status 请求。
- 前台运行中默认 2 秒；30 秒无变化后退避到 5/10/15 秒；状态变化后恢复 2 秒。
- 标签页隐藏时暂停普通轮询；回到前台立即刷新。
- 最近任务面板不可见时不刷新；批次能从当前 status 合并出的进度不再启动独立定时器。
- 导入会话和服装打标沿用现有接口，但必须遵守同样的“页面/面板不可见时暂停、同资源单在途、无变化退避、回到前台立即刷新”约束；上传中的本地进度优先来自上传队列，不通过频繁拉取全部历史会话重建。
- 加入 0–20% 抖动；暂不引入 WebSocket/SSE。

验收：status 原始响应小于 2 KB；单任务无变化观察 5 分钟不超过 50 次 status；20 个浏览器总状态流量不超过 15 MB/5 分钟；不存在 1.5 秒完整详情轮询；选搭完成、单张成片完成、重试、取消、替换输入和终态均有 `detailRevision` 契约测试。

### P0-5 GET 取消与旧响应隔离

- `api.request()` 支持 `AbortSignal`。
- 页面 GET/search/detail/status 在路由变化、组件卸载和筛选变化时取消。
- 每个资源使用递增 request token，旧响应即使返回也不能覆盖新页面。
- POST/PUT/DELETE、上传完成确认和已提交的 AI 任务不因切页自动取消。
- `<img src>` 不经过 `api.request()`，图片取消只作为浏览器 best effort；不为了可取消性改成 Blob fetch，也不承诺 Network 面板必须在 200 ms 内显示 cancelled。
- 图片浪费主要通过 preview、小范围预取、稳定 src 和卸载旧节点控制。

验收：快速 A/B/C 切换不会发生旧数据回写；API GET 能被取消；写操作状态不受切页影响。

### P0-6 浏览器全局上传队列

- 将当前每个调用点固定并发 4 改为单标签页共享的全局队列，默认并发 2，可配置为 1–3。
- 高 RTT、连续失败或上传期间 API 延迟明显恶化时，只提示运维调低配置；P0 不建设自动网络探测算法。
- 同一文件同一时间只有一个 PUT 或重试实例；重试使用退避和抖动。
- 页面切换不能重复创建同一上传；已有上传会话继续负责恢复业务状态。
- UI 展示“等待上传、上传中、处理中、可用、失败”。

预签名 PUT 发出后由浏览器直接访问 RustFS，FastAPI 无法可靠控制其实际并发，因此 P0 **不实现**服务端上传队列、队列位置、单用户配额或工作空间配额。多用户全局公平由真实瓶颈处的 QoS/AQM 负责。

验收：任意前端组件同时提交文件时，单标签页在途 PUT 不超过 2；不会因切页对同一文件重复创建 PUT；上传总字节仍约 200 MB。“上传期间 Web/SSH 仍可交互”属于组合体验目标，只在已确认并治理真实排队点时验收；不宣称仅将并发 4 改为 2 即可保证。

### P0-7 懒加载与首屏预算

- 非首屏图片使用 `loading="lazy"` 和 `decoding="async"`。
- 首屏最多 1–2 张关键图使用高优先级；普通缩略图保持 auto/low。
- 通过 IntersectionObserver 只加载可视区图片；12 张仅作为典型首屏测量样本，不是累计加载上限。大屏可见图片超过 12 张时仍必须自动全部加载，不得依赖点击、滚动重置配额。
- 图片检查器只加载当前 preview；可选预取相邻 1 张 preview，不预取 original。
- 现有列表已分页，P0 不引入虚拟列表；只有浏览器 Performance trace 证明最大页容量下 DOM、布局或内存是主要瓶颈时，才作为 P1 引入。

验收：冷启 24/30 张可见图片无需点击或滚动即可全部显示；滚动前不加载远离可视区的图片；打开检查器时只加载当前 preview 和至多相邻 1 张 preview；original 请求为 0。

### 条件基础设施项：工作守恒 QoS/AQM

- 先用 `iperf3`、RTT、重传和网关/主机指标确认真实瓶颈及方向。
- 只在真实排队点位于可管理的网关或主机，且项目具备配置与回滚权限时实施；若瓶颈在不可控的 FortiGate、VPN 隧道或上游线路，记录为外部依赖，不伪装成应用 P0 已完成。
- 在瓶颈处使用公平队列/AQM，把 API/SSH/控制请求设为交互流量，把图片上传、原图下载和导出设为 bulk。
- QoS 必须工作守恒：无竞争时 bulk 可使用空闲带宽，有竞争时主动让路；不把 bulk 永久硬限制为 60%–70%。
- 整形总上限应略低于实测瓶颈以控制队列，具体数值由现场链路确定。
- 若 API、RustFS 和 SSH 端口/入口无法被网关区分，先调整入口、标记或代理策略；不得假设网关能识别 HTTPS 中的 URL。
- 上下行分别验证；provider 出站流量与用户媒体流量分别计量。

验收：同一链路、同一时段对比空闲与 bulk 满载；满载时 status p95 和 SSH 回显 p95 相对各自空闲基线增量不超过 100 ms，且不超过基线的 2 倍。当基线 RTT 允许时，同时以 status p95 <300 ms、SSH 回显 p95 <150 ms 作为体验目标；没有持续 10 秒以上的丢包/重传异常；链路空闲时 bulk 可以使用未被交互流量占用的带宽。

## 5. P1：只有数据达到门槛才实施

| P1 项目 | 初始启动门槛 | 收敛后的实现边界 |
|---|---|---|
| 剩余图片入口统一直传 | 25 MB 级上传期间 FastAPI RSS 连续 3 个 1 分钟窗口高于空闲基线 30%，或 API p95 连续 3 个窗口超出基线 2 倍 | 迁移大图片入口；收益定位为降低 API CPU/RSS，不宣称减少用户到服务器的 WAN 字节 |
| 图片派生有界后台处理 | 导入期间 CPU 连续 3 个 1 分钟窗口 >85%，或非导入 API p95 超出空闲基线 2 倍，且分段计时确认 Pillow 为主因 | 复用 SQLite 持久作业和单机 1–2 worker，不引入 Redis、Kafka、Celery 集群 |
| S3 multipart 分片重试 | 大于 32 MB 的文件在至少 50 次真实上传中整文件重传率 >2%，或一个业务周期内失败重传超过 2 GB | 只重传失败 part；刷新后允许用户重新选择同一文件继续，不承诺无感跨刷新读取本地文件 |
| 导出公平队列 | 2 个并发导出使 status p95 或 SSH 回显 p95 连续 3 个窗口超出空闲基线 2 倍，或磁盘 `%util` 持续 >85% | 单机全局 1–2 个导出作业；否则只依靠已验证的 QoS 或一次导出并发限制 |
| 媒体热路径减少 HEAD | 媒体冷请求分段计时中 RustFS HEAD 耗时占 p95 路径超过 40%，且媒体 p95 未达现有 Runbook 目标 | 使用数据库可用状态；浏览器图片失败后上报轻量 missing 事件，或由后台巡检闭环，不能假设 FastAPI 能看到 302 后的 RustFS 404 |
| 轻量 GET 去重/短缓存 | 同页同参数重复 GET 占 5 分钟 API 请求数或传输字节 >10% | 先做在途 Promise 去重和 5–15 秒小缓存；不实现完整 SWR、订阅引用计数或自研 React Query |
| 列表虚拟化 | 最大分页容量下，滚动或筛选的主线程长任务连续出现，且布局/DOM 而非图片传输是主因 | 只虚拟化被证实的列表，保留键盘访问、批量选择和滚动恢复；不先引入通用虚拟列表抽象 |

上述是 0.1.0 的初始决策门槛，可根据第一个完整业务周期的基线调整，但调整后必须在实施 P1 前记录新门槛和样本量，不使用“感觉很慢”作为单独立项依据。

### 5.1 multipart 的明确限制

- 服务端保存 `uploadId`、已完成 part 和 ETag，不等于浏览器刷新后仍持有本地文件。
- 通用浏览器刷新后需要用户重新选择同一个文件；校验文件名、大小、lastModified 和首尾摘要后才能继续。
- 不把 File System Access API 作为 0.1.0 必需能力。
- multipart ETag 不默认等同于完整文件哈希；完整性校验必须依据 RustFS 实际支持的 checksum 能力设计。

### 5.2 单机直传收益边界

默认生产是 frontend、backend、RustFS 同机。把剩余 multipart 改为浏览器直传，不会让用户到服务器的 100 Mbps 链路少传一份原图；主要收益是绕过 FastAPI 请求体、内存、临时文件和应用层转写。因此该项由 API 资源指标决定，不作为带宽 P0。

## 6. 单人业务操作对比

下表使用第 2.2 节假设。P1 未达到启动门槛且不具备网络治理条件时，“按证据全部实施”与 P0 相同。

| 业务操作 | 当前实现 | P0 实现 | 按证据全部实施目标 |
|---|---|---|---|
| 冷打开 30 图列表，派生图正常 | 约 0.9–1.0 MB；列表 JSON 占主要部分 | 约 0.25–0.4 MB；轻列表 + thumb | 约 0.2–0.3 MB；按可视区优先显示 |
| 冷打开列表，1 张 thumb 缺失并回退原图 | 约 26 MB，单张异常即可拖慢整页 | 约 0.25–0.4 MB；异常图显示占位，不下载原图 | 同 P0；可增加 missing 上报和后台修复 |
| 连续查看 10 张图片 | 约 250 MB；默认直接加载原图 | 约 1.5 MB preview | 约 1.5 MB；仅当前图和至多相邻 1 张 preview |
| 查看 10 张，其中明确查看 2 张原图 | 约 250 MB | 约 51.5 MB | 约 51.5 MB；原图仍是用户明确成本 |
| A 页面加载中快速切换到 B | 可能继续浪费约 2–27 MB，并有旧响应覆盖风险 | API GET 被取消，图片 best effort 停止；通常只剩少量在途 preview | 同 P0；若重复 GET 明显，可增加在途去重 |
| 上传 8 张 × 25 MB，无失败 | 总量约 200 MB；4 并发容易形成 bufferbloat | 总量仍约 200 MB；全局并发 2，降低突发与连接竞争，但不承诺单独消除 bufferbloat | 若排队点可控，工作守恒 QoS 保护交互；直传补齐只降低 API CPU/RSS |
| 上传中 1 张在 75% 失败 | 额外重传约 18.75 MB，总量约 218.75 MB | 基本不变；P0 不为偶发失败建设 multipart | 若失败率触发 multipart，通常额外 4–8 MB，总量约 204–208 MB |
| AI 生成 5 分钟，仅观察状态 | 约 33.9 MB / 约 0.9 Mbps | 不超过约 0.75 MB；轻量 status + 退避 | 约 0.5–0.75 MB；重复 GET 明显时再去重 |
| 成片完成后点击查看 5 张 | 约 125 MB 原图 | 约 0.75 MB preview | 约 0.75 MB |
| 明确下载 5 张成片 | 约 40 MB | 仍约 40 MB；不虚构减少原始字节 | 若排队点可控，将下载作为 bulk；必要时受导出队列公平调度 |
| 短时间再次进入同一列表 | 取决于稳定 src 和缓存，可能重复请求 | 浏览器 HTTP cache 命中，传输接近 0 | 同 P0，不增加前端图片缓存系统 |

## 7. 多人同时操作对比

| 业务操作 | 当前实现 | P0 实现 | 按证据全部实施目标 |
|---|---|---|---|
| 10 人同时观察 AI 任务 5 分钟 | 约 339 MB / 约 9 Mbps | 不超过约 7.5 MB / 约 0.2 Mbps | 约 5–7.5 MB |
| 20 人同时观察 AI 任务 5 分钟 | 约 678 MB / 约 18 Mbps | 不超过约 15 MB / 约 0.4 Mbps | 约 10–15 MB |
| 5 人同时冷打开正常 30 图列表 | 约 4.5–5 MB 突发 | 约 1.25–2 MB，thumb 分批加载 | 约 1–1.5 MB，优先首屏 |
| 5 人列表各遇到 1 张原图回退 | 约 130 MB 突发 | 约 1.25–2 MB；异常图占位 | 同 P0；后台渐进修复 |
| 5 人各查看 10 张图片 | 约 1.25 GB | 约 7.5 MB preview | 约 7.5 MB |
| 5 人同时各上传 8 × 25 MB | 总量约 1 GB；多组 4 并发易挤占链路 | 总量仍约 1 GB；每标签并发 2，减少突发，但多人全局公平不由前端保证 | 若排队点可控，工作守恒 QoS 保护 API/SSH；只有实测需要时才增加对象存储/网关级公平策略 |
| 5 人同时各下载一组 40 MB 成片 | 总量约 200 MB，可能造成下行排队 | 总量仍约 200 MB；应用不伪造总字节减少 | 若排队点可控，下载作为 bulk；若导出影响达到门槛，再增加单机公平队列 |
| 5 个首次 AI 任务的 provider 媒体流量 | 取决于参考图与结果大小，示例可达约 550 MB 级 | 字节数基本不变；与用户媒体分开计量和限并发 | 复用已有不可变媒体缓存；只限制并发，不牺牲任务正确性 |
| 上传、下载、状态观察同时发生 | 可能因 bufferbloat 导致 Web 和 SSH 同时卡顿 | 轻量状态与上传并发限制降低压力，但不承诺消除不可控网络排队 | 排队点可控时由 AQM/QoS 使 bulk 让路；P1 队列只在仍不足时增加 |

## 8. 测试与验收

### 8.1 标准场景

1. mock AI 任务运行 5 分钟，单人、10 人、20 人只观察状态。
2. 30 图列表与 10 图检查器，分别测试冷缓存、热缓存和派生图缺失。
3. 8 × 25 MB 单人上传，同时持续请求 status 并记录 SSH 回显探针；应用 P0 验收上传并发、状态流量和基线差异，不在未治理的外部网络上强制承诺 SSH 绝对值。
4. 只有条件基础设施项已启用时，才运行 5 人上传、浏览和下载混合场景，验证工作守恒 QoS/AQM。
5. A/B/C 页面每 300 ms 切换，后端人为延迟 1–3 秒，验证取消和旧响应隔离。
6. 只有 multipart 达到 P1 启动条件后，才执行 60%/90% 断网分片恢复测试。
7. 所有场景使用临时数据库、专用对象前缀和 mock provider。

### 8.2 P0 总体验收门槛

| 指标 | P0 门槛 |
|---|---:|
| status 原始响应 | <2 KB |
| 单浏览器 AI 状态流量 | <0.1 Mbps |
| 20 浏览器 AI 状态总流量 | <0.5 Mbps |
| 30 图冷列表总流量 | <2 MB，目标 0.25–0.4 MB |
| 普通列表/默认检查器 original 请求 | 0 |
| 单标签页上传 PUT 并发 | 默认 ≤2 |
| 轮询协调 | 页面/面板不可见时暂停；同资源单在途；无变化按规则退避 |
| 快速切页旧数据回写 | 0 |
| 热列表媒体传输 | 接近 0；必须说明浏览器缓存条件 |

所有结果必须同时记录测试链路的有效上下行、基线 RTT、丢包率、主机规格和缓存状态；脱离前提的单个耗时数字不作为结论。

## 9. 发布与回滚

### 9.1 最小配置与兼容回滚

- 不为本轮优化建设通用 feature flag 系统。
- 只保留 `upload_concurrency` 数值配置，默认 2，允许运维在 1–3 之间调整。
- status 端点为增量契约；上线后至少保留一个业务周期的旧详情 GET，前端回滚时可继续使用，不需要 `task_status_polling_v2`。
- preview-first 先补齐活跃派生图并上线新 DTO，再切换后端缺失行为；回滚时回到“占位 + 用户显式原图”，不恢复自动原图 fallback，也不需要长期 `media_no_original_fallback`。
- gzip、轻列表 DTO、GET Abort、lazy loading 和 request token 使用正常版本回滚。

### 9.2 发布顺序

1. 使用现有 Runbook 记录轻量基线。
2. 上线 gzip、轻列表 DTO、GET 取消和旧响应隔离。
3. 补齐活跃派生图，上线 preview-first，再开启禁止原图兜底。
4. 上线轻量 status、单一 `detailRevision` 和任务/导入/打标轮询协调。
5. 上传并发改为单标签页全局 2。
6. 确认真实排队点且具备控制权后，再配置工作守恒 QoS/AQM；条件不成立时记录外部依赖并跳过。
7. 运行一个完整业务周期，只有指标达到第 5 节门槛时才立项对应 P1。

数据库新增 `detailRevision` 采用向前兼容迁移；回滚应用时保留字段。禁止原图兜底回滚时优先回到“占位 + 用户显式原图”，不得直接恢复自动原图 fallback。

## 10. 开发拆分与完成定义

| 迭代 | 内容 | 可独立交付结果 |
|---|---|---|
| Iteration 0 | 轻量基线 | 能区分 API、媒体、上传、下载和链路问题 |
| Iteration 1 | P0-2、P0-3、P0-5、前端懒加载 | 浏览和切页立即减少无效流量 |
| Iteration 2 | P0-4 | AI 状态流量数量级下降 |
| Iteration 3 | P0-6、P0-7 | 上传突发和首屏媒体请求受控，不对不可控网络做虚假保证 |
| Conditional Network | 真实排队点可控时实施 QoS/AQM | bulk 满载时交互延迟增量达标 |
| Conditional P1 | 第 5 节中被数据触发的单项 P1 | 只解决已证实的剩余瓶颈 |

每项完成必须满足：

1. 契约、配置和向前兼容迁移完整；
2. 自动化测试不触发外部 AI/provider；
3. 使用隔离数据保存上线前后同口径结果；
4. 未达到验收门槛时给出原因，不只标记“已优化”；
5. 更新前后端实现文档、部署文档和负载测试 Runbook 中的实际配置。

## 11. 明确不做

- 不引入 CDN、公共 OSS 或跨地域媒体加速；
- 不优先引入 WebSocket/SSE；
- 不压缩或降质商品原图；
- 不建设服务端预签名 PUT 排队位置、单用户/工作空间配额或分布式上传调度；
- 不承诺浏览器刷新后无需重新选择本地文件即可续传；
- 不把 302 后 RustFS 的 404 当作 FastAPI 自动可见事件；
- 不为图片取消改用 Blob/IndexedDB/Service Worker 缓存；
- 不预建 Redis、Kafka、Celery 集群或复杂监控平台；
- 不通过真实 provider 执行性能压测。

## 追加：渐进加载体验补齐（2026-09-21）

前述基线保留为当时的测量与方案记录，不将历史缺口误认为当前实现。本轮基于已落地的 thumb/preview/original 分层、分页、GET 取消、轻量轮询和共享上传队列，收敛到四项前端改动：

1. 统一图片加载占位、失败反馈与同 URL 单图手动重试。
2. 搭配服装库与生成记录首次骨架屏，有旧内容时刷新保留并标明更新中。
3. 大图检查器使用当前图片的 thumb/已加载 preview 过渡，原图显式加载，切图重置。
4. 列表读取失败与空结果分离，局部重试，不吞掉失败后误报空数据。

本轮不实施额外预取、首屏优先级调整、初始化路由恢复拆分、自定义带宽调度、虚拟列表或新缓存系统；后续只有真实弱网验证显示明显瓶颈时才重新评估。验收通过隔离的 mock 接口和图片完成，不触发外部 AI，也不修改共享业务数据。产品交互细节以 `../03_ux_guide/user_uiux.md` 第 10 节为准。


## 可见页面的静默自动刷新

姿势库、搭配服装库、生成记录、最近任务和模特背景采用持久化集合版本检查。无变化的空闲页面每分钟约 2 次单行数据库读取，JSON 响应只有版本号；不重复装配列表、传输标签或加载图片。有可见运行条目时检查间隔 5–18 秒；版本变化才读取当前页或展开的详情，单个协调器始终串行，失败指数退避到基础间隔 120 秒并加抖动。隐藏标签页、离线、离开页面或切到素材导入面板后暂停对应检查，恢复时检查一次。

自动更新不使用用户翻页/筛选的 loading 反馈；不改变布局、透明度、分页可用性、选择或滚动状态。JSON 未变保持对象引用，图片沿用稳定 URL 和浏览器缓存。服装详情的未保存图片草稿不被自动更新覆盖。

成本不是零：每个可见标签页仍有 HTTP/认证及一次数据库连接开销，业务写入增加常数规模的版本计数更新；数据持续变化时仍需读取列表。当前服装筛选接口包含全库筛选项计算，因此不应恢复成高频完整列表轮询。此实现没有跨标签页主节点或推送服务；大量同时可见客户端下仍应通过访问日志测量 QPS 和延迟，再决定是否需要进一步优化，不宣称已经完成生产容量压测。
