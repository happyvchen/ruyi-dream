# 已弃用方案：单次 Gemini 选搭 ID

## 1. 方案摘要

本方案曾用于新版 AI 摄影棚的早期 MVP 选搭阶段。它的核心思路是：

```text
主推款图片 + READY 搭配服饰 effective_tags
-> Gemini 单次判断
-> selected_material_ids + hero_visual_summary + reason_summary + warnings
```

后端只把主推款图片和全量 READY 搭配服饰压缩标签交给 Gemini。Gemini 返回一个 ID 数组，后端校验这些 ID 是否存在且属于 READY 服饰，然后把选中服饰快照写入 `generation_stylings`。后续 `ShotPlan` 和 Image-2 预览/成片阶段读取这些选中服饰。

旧输出形态：

```json
{
  "selected_material_ids": [1, 2],
  "hero_visual_summary": "极短主推款视觉摘要",
  "reason_summary": "极短选择理由",
  "warnings": []
}
```

旧职责假设：

- Gemini 智能选搭只负责从搭配服饰库选择配角服饰。
- ShotPlan 后续再决定穿着关系、镜头和拍摄方案。
- Image-2 只负责按主推款、搭配服饰和 ShotPlan 生成视觉结果。

这个方案的优点是实现简单、接口轻、容易跑通 MVP。但实际验证表明，它把“服装搭配”过度简化成了“从候选里挑几个 ID”，不足以支撑生产级电商商品摄影。

## 2. 失败案例

### 2.1 task=1：连衣裙主推款被双外套误配

任务：

- 主推款：`125209G7986419`
- 视觉摘要：深蓝色 V 领短袖牛仔连衣裙，附带棕色收腰皮带，职场休闲风。

旧方案选中：

- `125329C2931716`：米色西装外套，标签包含 `coverage_risk: may_cover_hero`
- `125359C2906732`：深棕西装外套

旧理由：

```text
选择西装外套以提升通勤感。米色可形成干练撞色，棕色与腰带色系呼应。
```

问题：

- 一件连衣裙主推款本身已经是完整 look，不一定需要库内搭配服饰。
- 两件西装外套不能作为同一套真实可穿 outfit 同时穿着。
- 外套会遮挡连衣裙的 V 领、前襟纽扣、腰带、口袋和裙身比例。
- Gemini 的理由停留在“通勤感”和“颜色呼应”，没有评估主推款是否被弱化。

### 2.2 task=2：阔腿裤主推款被整套造型吞掉

任务：

- 主推款：`125219C5920601`
- 视觉摘要：白色高腰阔腿西装裤，挺阔压褶设计，配同色系极细腰带。

旧方案选中：

- `125349C0909601`：白色马甲
- `125359C2906732`：深棕西装外套
- `125359TK944711`：深棕针织衫

旧理由：

```text
选取同色系马甲打造极简都会风；利用深棕色针织与西装进行撞色叠穿，构建干练的秋冬职场通勤造型。
```

问题：

- 这套 outfit 作为通勤造型有一定成立性，但它不再是“以白色阔腿裤为主角”的商品摄影方案。
- 画面重心容易转移到白马甲、棕西装和整套秋冬通勤氛围。
- 裤子的高腰、褶裥、腰带、垂坠和裤腿比例没有在选搭阶段被设为最高优先级。
- 旧方案只判断“整套是否好看”，没有判断“这套是否让主推裤子更好卖”。

## 3. 根因分析

### 3.1 抽象层级错误

服饰搭配不是简单分类或检索任务。它同时包含：

- 主推款商品理解
- 品牌审美判断
- 场景和季节语境
- outfit 可穿性
- 主推款商品可见性
- 电商棚拍图位目标
- 生成模型可执行性

旧方案直接要求 Gemini 输出 `selected_material_ids`，跳过了造型师本应完成的思考过程。模型即使有审美能力，也没有被要求交付完整方案、备选方案、自评和拒绝理由。

### 3.2 目标函数不清

旧方案隐含目标是：

```text
选择适合一起穿到模特身上的配角服饰。
```

但生产场景真正目标是：

```text
为主推款生成一套能提升商品表达和电商转化的棚拍造型方案。
```

这两个目标不同。前者容易选出“整体好看”的 look，后者必须保证主推款始终是视觉和商业中心。

### 3.3 缺少 outfit 级别验证

旧后端只校验：

- ID 是否合法
- 是否 READY
- JSON 是否可解析

它不校验：

- 选中组合是否是一套可穿 outfit
- 是否选择了多个互斥外套或上装
- 是否遮挡主推款核心卖点
- 是否让配角服饰成为视觉中心
- 是否允许空选搭作为优秀结果

因此 `[4, 9]` 这种“双外套搭连衣裙”的结果能直接进入后续流程。

### 3.4 ShotPlan 接手太晚

旧设计把“穿着关系和商品展示重点”留给 ShotPlan，但 ShotPlan 的输入已经是错误选搭结果。等到 ShotPlan 阶段再修正，通常只能缓解问题，不能改变“选错了配角”这个事实。

选搭阶段必须先判断：

- 是否需要库内搭配服饰
- 选择哪些服饰
- 它们如何穿着
- 主推款哪些卖点必须露出
- 哪些候选方案因为遮挡或喧宾夺主被拒绝

这些都应属于 `StylingPlan`，不是等到 ShotPlan 再补救。

### 3.5 复盘信息不足

旧 attempt 的 request snapshot 曾出现 `{}`，只保存了 response。这样无法复盘：

- 当时有哪些候选服饰
- 候选 tags 是否污染
- prompt 如何表达任务
- 模型有没有看到风险字段
- 为什么拒绝或没有拒绝其它方案

生产级链路必须保存完整输入、候选召回、prompt 和每步结构化输出。

## 4. 弃用原因

本方案被弃用，不是因为 Gemini 没有审美能力，而是因为产品和工程没有给 Gemini 一个足够正确的工作流。

主要弃用原因：

1. **输出太薄**：只输出 ID，不能表达完整造型方案。
2. **无法鼓励探索**：模型没有空间提出多个造型方向并比较优劣。
3. **无法自我批判**：没有审美、品牌、主推款可见性、商业可用性的评分维度。
4. **容易喧宾夺主**：整套 outfit 好看不等于主推款更好卖。
5. **难以复盘**：缺少候选快照、拒绝理由和完整 request snapshot。
6. **ShotPlan 依赖错误上游**：一旦选搭错了，后续分镜只能补救，不能根治。

## 5. 替代方案

当前权威方案为 `AI Stylist / StylingPlan` 工作流：

```text
主推款理解
-> 候选召回
-> 造型意图探索
-> 多套 outfit 候选
-> Stylist Critic 自评
-> 选中 StylingPlan
-> ShotPlan
-> Image-2 六宫格和最终成片
```

核心变化：

- 把 Gemini 从“ID 分类器”提升为“造型总监”。
- 让模型自由探索多套方案，但必须输出结构化理由、评分和风险。
- 允许空的库内搭配成为优秀结果。
- 把主推款可见性和商业可用性作为选搭验收维度。
- 后端只保留真实性、状态合法性、可穿性和商品主角等生产边界，不把审美写死成大量规则。
- `ShotPlan` 必须承接 `StylingPlan`，而不是从选中 ID 反推造型意图。

## 6. 可保留资产

虽然旧方案被弃用，以下资产仍可复用：

- READY 搭配服饰过滤。
- `effective_tags` 压缩卡片。
- 主推款图片冻结为 `GenerationTaskInputVersion`。
- 选中搭配服饰快照。
- `selected_material_ids` 作为从 `StylingPlan` 派生出的关系索引。
- provider attempt 机制。
- 后台状态机和前端轮询。

以下内容不再作为设计依据：

- Gemini 单次返回 ID 即完成选搭。
- “选搭不负责穿着关系”的职责边界。
- request snapshot 为空或只保存 response。
- ShotPlan 从选中 ID 反推完整穿着方案。

## 7. 结论

旧方案适合快速 MVP 验证，但不适合生产级服饰品牌视觉生成。它的问题不是缺少更多硬规则，而是缺少正确的造型工作流。

新版方案的核心判断是：

```text
不要把 Gemini 当分类器，要把它当造型总监；
但造型总监必须交 StylingPlan、备选方案、评分、风险和拒绝理由。
```

这份归档文档只作为过程记录。当前实现和后续设计应以 `design/01_generation_flow/generation_flow.md`、`design/01_generation_flow/generation_responsibility_matrix.md` 和相关权威文档为准。
